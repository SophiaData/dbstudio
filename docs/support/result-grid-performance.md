来源：[GitHub 45966772547](https://github.com/SophiaData/dbstudio/actions/runs/45966772547) 的 `native-page-performance` 产物。分页原生、COUNT 真库与浏览器测量步骤通过；该运行随后因 Redis/Kafka 夹具启动退出而整体失败，不能引用为完整 CI 通过。

## 环境和边界

- Linux x64，Intel Xeon 6975P-C，4 逻辑 CPU，约 15.3 GiB 内存；Node 24.22.3，Chrome 157.0.8103.78，1600×1000，单 worker。
- PostgreSQL 17.12 / 512 MiB 容器，MySQL 8.0.46 / 1024 MiB 容器；每表 10 万或 100 万行、4 列，包含 ID、BIGINT、DECIMAL(30,18) 与中文。未清数据库缓存。
- 每种方言×行数×页大小×首屏/下一页/深页，共 24 场景，各 5 次。首屏调用 runQuery，下一页和深页调用 fetchResultPage；深页 offset=总行数−页大小。
- 原生 wallMs 是 Driver::call 总耗时，包含数据库 I/O 与原生转换，排除建表/填充、检查、写文件与 IPC；不是纯服务器耗时。
- 渲染为真实页面数据已到达后，生产 ResultGrid/useWorkbench 重新挂载至 nextTick+两次动画帧的耗时；Vite 开发环境，不含传输/解码/卸载，不代表安装版 Tauri 端到端延迟。
- 原生和渲染不能相加成端到端耗时。五次采样的最近秩 p95 等于最大值；尚未设延迟 SLO。

## 正确性与后续判断

120 次原生调用和 120 次渲染均完成。独立数据库连接核对总行数，原生及 DOM 逐行核对 ID、高精度数字和中文，首尾焦点无遮挡；浏览器每次最多加载 1000 行。每个真实页样本有 SHA-256，报告绑定源码 SHA。

MySQL 百万行各页耗时接近且明显高于 PostgreSQL：当前 MySQL live 分页会重新执行原查询，并在读取所需页后排空剩余协议数据（mysql.rs 的 page/page_with_snapshot）。这是后续取页策略评估的重点，本次未改变分页语义。每页 1000 行挂载也比 200 行慢，默认仍保留 200；是否引入虚拟滚动需另有交互和内存测量，当前不据此扩展重构。

COUNT 取消真库套件明确执行 PostgreSQL/MySQL 两项并通过；这与分页耗时是独立证据。Windows 安装版、本机网络、真实业务宽表和长期稳定性尚未由本报告覆盖。
