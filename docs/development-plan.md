# DBStudio 日常数据库与数仓工作台开发规划

日期：2026-11-25  
版本：0.2，扩展到数仓日常主力工具目标。  
状态：P1.1、P1.2 已通过 Windows 候选包验收；P1.3 执行错误定位与大文本测量实施中，尚未完成全部 P1 验收。
执行方式：主代理单线程推进，每次完成一项；GitHub 承担完整测试和打包。

## 1. 产品目标与投入原则

目标是让 DBStudio 成为用户愿意每天打开的数据库与数仓工作台。先覆盖找表、编写 SQL、查看结果、修改数据和继续上次工作，再覆盖 Hologres/MaxCompute 查数、复杂 SQL 开发、DataWorks 节点排障及本地开发交付。

用户已明确不愿继续使用 DBeaver。后续以 DBStudio 的实际使用感受决定优先级，dbx 用于参考成熟交互和检验遗漏。验收不要求用户重新使用 DBeaver。

继续开发的价值应体现在具体任务上：更容易找到对象，写 SQL 更顺手，宽表更容易看，修改和提交更清楚，重开应用能继续工作。通过 CI 是交付基础，用户实际愿意使用才是产品目标。每个阶段交付可安装版本，体验不达标时先修正当前阶段，再进入下一项。

首轮聚焦 Windows x64、MySQL 日常查询与编辑，同时维护 PostgreSQL、SQLite 的既有查询行为。第二轮将 Hologres、MaxCompute 和 DataWorks 列为正式实施阶段，见第 10 节；Hologres 必须专项验证，不能由 PostgreSQL 测试通过直接推断。

| 交付层次 | 达成条件 | 可以如何定位 |
| --- | --- | --- |
| 基础日用版 | P0–P4 通过 | 可承担约定范围的日常 MySQL 查询与数据维护 |
| 数仓查询版 | 再完成 W0–W3 | 可在一个工作台查 Hologres/MaxCompute、编写常用复杂 SQL、追踪异步查询 |
| 数仓主力候选版 | 再完成 W4–W6，并通过 12 个必选场景和连续试用 | 可承担约定的查数、SQL 开发、节点排障、对账与本地交付任务 |

“主力”以第 10.5 节的明确任务集合判定。DataWorks 最终提交/发布以及生产写授权保留平台流程，应用提供经核对的草稿和跳转入口；这不应要求用户回到 DBeaver 完成日常查询。完整 DBA 管理和所有 dbx 功能的等价覆盖另行评估。

## 4. P1：先把 SQL 编辑器做好

### 4.1 技术选择与边界

采用 CodeMirror 6，按需引入 SQL 语言、搜索、补全、历史和视图相关模块。P1.1 已开始接入 state/view/commands/language/lang-sql，所选包为 MIT 许可，版本锁定在项目锁文件；Tauri WebView 与生产安装包兼容性须由本提交的 GitHub 验收证明。

编辑器负责文本、选区、光标、撤销和交互。执行仍经过现有工作台与 Tauri 后端：复用语句切分、参数绑定、连接捕获、取消和事务逻辑。编辑器的语法分析不得自行决定执行哪些 SQL，也不得绕过现有执行入口。

每个 SQL 标签独立维护编辑状态，避免切换标签时将全文重新写入编辑器而破坏撤销栈。运行中的执行请求继续绑定发起时的标签和连接；后续切换侧栏或标签不能改变该请求的目标。

### 4.2 顺序拆分

| 小项 | 内容 | 预期结果 |
| --- | --- | --- |
| P1.1 编辑器接入 | 替换输入控件，接入现有 SQL 状态与执行接口；行号、高亮、括号匹配、缩进、撤销重做、中文输入 | 可以正常编辑并执行，现有参数与快捷键行为不退步 |
| P1.2 日常编辑 | 查找替换、行注释、折叠、自动换行开关；按标签保留选区、光标和滚动；接入现有元数据补全 | 常用编辑任务可以在键盘上连续完成，补全不串连接 |
| P1.3 错误反馈与交付 | 定位失败语句；有可靠错误位置时标记行列；完善大文本和可访问性验证，生成试用安装包 | 用户知道哪条语句失败，修正后可继续执行；安装版操作可验证 |

错误定位必须使用可验证的信息：将执行时的语句范围与返回错误关联。只有驱动明确提供可靠位置且映射经过验证时才展示精确行列；否则定位失败语句并展示原始错误。若用户已修改文本，保留执行快照提示，不把旧错误标在新文本的错误位置。

首版补全继续覆盖当前连接中已加载的表、字段和单层 SELECT/JOIN 别名。CTE、嵌套子查询和跨语句语义诊断作为后续增强项，遇到无法解析的作用域应收敛候选，不混入其他连接的字段。

### 4.3 首阶段验收用例

| 编号 | 操作 | 必须观察到的结果 |
| --- | --- | --- |
| E01 | 输入中文注释和字符串，换行、粘贴、撤销、重做 | 文字完整；输入法候选确认不触发 SQL 执行或错误补全 |
| E02 | 在含注释、字符串分号的多语句 SQL 中执行当前语句、选区、全部 | 范围与现有执行约定一致；写操作不重复执行 |
| E03 | 打开补全后使用 Ctrl/Cmd+Enter、Shift+Enter、Enter/Tab、Esc | 执行、接受候选和关闭候选的行为明确；快捷键互不抢占 |
| E04 | 两个连接各有同名表，在标签间切换并使用别名补全 | 候选和执行目标属于当前 SQL 标签；重复 schema 名称不会导致混列 |
| E05 | 查找替换、注释、折叠，再切换标签并撤销 | 文本、选区和撤销状态不串标签；格式化不改变字面量内容 |
| E06 | 执行参数 SQL，取消输入后重试；缺参数时执行 | 取消不执行；缺参在首次执行前拒绝；绑定规则保持正确 |
| E07 | 制造 SQL 错误、取消慢查询、随后再执行查询 | 原错误保留、定位可信、状态解除；后续查询能继续；不误报取消成功 |
| E08 | 在生产安装包中输入、选区执行、使用查找和补全 | 真实键盘和中文输入可用；自动化通过新编辑器真实入口操作 |
| E09 | 编辑 1,000 行和 10,000 行合成 SQL，切换 10 个 SQL 标签 | 记录输入响应、切换时间与内存；无丢字、明显卡顿或持续增长趋势，未达标先定位原因 |

快捷键以 Windows 使用为优先，同时维护 macOS 映射。P1 不更改 SQL 文本的执行含义或连接级事务语义。

## 5. P2：让结果表格适合每天使用

按以下顺序交付，每个小项验证后再继续：

1. **宽表可读**：拖动列宽、自动适宽、固定关键列、隐藏和恢复列、按名称跳转列。复制和粘贴的列映射以实际可见列顺序为准，并明确隐藏列不参与的规则。
2. **选择与复制**：支持键盘移动、Shift 连续选择、当前页矩形复制；完整文本获取失败时提示，不能悄悄复制截断预览。明确带表头与不带表头、NULL 与空串的输出规则。
3. **分页与筛选**：拟提供 100/200/500/1,000 行页大小，默认保留 200；修改页大小回到第一页，先处理未应用草稿。服务端筛选与本页搜索必须明确区分；总行数按需统计，取消可用。跳页及更大单页上限根据实测代价另行决定。
4. **统一修改确认**：MySQL 所有会应用本地 UPDATE 草稿的路径复用预览。直接提交涉及同连接多个标签时，一次列清各表修改与事务范围；取消不写入、保留全部草稿。已有未提交事务与本次新增草稿分别说明。其他数据库维持原有行为，另行验证后扩展。

重点验收：列隐藏/固定后复制粘贴不偏列；NULL、空串、超大整数、小数不损失；跨页粘贴整批拒绝；更改页大小或筛选取消后保留草稿；同连接两表修改取消无副作用，确认后独立连接回读一致。

对 10 万行和 100 万行专用合成表测量首屏、下一页和深翻页，分别记录数据库耗时与界面可用时间。大表分页不等于把百万行加载到前端。虚拟滚动是否必要、数据库取页策略是否需要调整，由测量决定，不先做无证据的性能重构。

## 6. P3：让工作区清楚、可恢复

现有 SQL 标签和草稿恢复是基础，本阶段完善以下行为：

- **目标始终可见**：编辑器和结果区显示所属连接、配置默认库及已知的会话库信息；发生变化或无法确认时明确提示。侧栏选择不悄悄改变执行目标。MySQL `USE` 对同连接其他标签的影响必须可解释。
- **接着上次工作**：保留标签顺序、活动标签、布局和必要的编辑器位置。恢复 SQL 草稿时不自动执行 SQL，不声称恢复服务器事务；过期结果明确标识，用户主动刷新。
- **找对象更直接**：同名表标明连接和 schema；搜索说明已加载范围或服务端搜索范围；展开、刷新和导航不丢当前编辑内容。
- **失败可继续处理**：断连、重连失败、草稿存储失败均有可见状态。重连后不自动重放写操作；提交状态未知时先提示核对，不显示成功或诱导盲目重试。

验收覆盖：两个连接的同名表、多个 SQL 标签切换、正常退出重开、存储失败、数据库断开再恢复。持久化改动采用可兼容的版本策略，写失败保留当前内存草稿；迁移失败保留原文件并给出恢复办法。

## 7. 性能与日常使用验收

P0 在固定 Windows 设备、固定数据集和同一连接条件下采集基线；区分冷启动和热启动，记录应用版本、数据规模和重复次数。GitHub 用于正确性与构建验收，用户设备用于实际响应体验判断。

| 观察项 | 测量方式 | 规划目标，尚非实测成绩 |
| --- | --- | --- |
| 输入与补全响应 | 对同一合成 SQL 连续输入/触发 30 次，记录动作到可见反馈 | 常用规模下 p95 不超过 100 ms；大文本单独记录，避免主观宣布流畅 |
| 标签切换 | 10 个 SQL 标签间切换 30 次，记录切换到可编辑 | p95 不超过 200 ms，光标、草稿和连接不串位 |
| 启动可用时间 | 冷启动与热启动各 5 次，分别记录中位数 | 先与 P0 基线比较；明显变慢时定位并解释，P0 后确定绝对阈值 |
| 大结果交互 | 同一合成表测首屏和分页，数据库与渲染分别计时 | 有界读取、可取消，无静默漏行或重复行；耗时阈值待基线确定 |
| 持续使用 | 8 小时活跃连接与定时查询，结束后编辑回滚、导出、关闭 | 无未解释的资源持续增长、丢稿、事务误报；中断或跳过不得计为通过 |

响应指标需由测量工具或操作录像给出可复核结果；未测量则记“未测”，不得用 CI 总耗时代替。P4 试用以用户完成日常操作为主，每次只记录最影响工作的阻塞，顺序修复。

达到第一轮的日常使用目标，需要同时满足：约定的编辑/查询/结果操作能完成、关键数据正确性与恢复问题关闭、用户确认愿意继续使用。第二轮数仓主力候选版另须通过第 10.5 节的必选场景。完整替代所有数据库管理工具、全部 M01–M23 契约通过和正式生产放行，不由任何单次 CI 通过自动宣布达成。

## 8. 验证、交付与回退规则

通用完整测试和打包走 GitHub，串行等待各项完成；Cargo 使用单构建任务，Rust 测试与前端核心单测使用单 worker。本地只做必要的最小复现；需要构建缓存时放 E 盘。所有数据库写入测试使用隔离合成实例。第二轮云服务验收另见第 10.4 节：GitHub 上的模拟服务不能证明企业 Hologres、MaxCompute 或 DataWorks 已适配。

执行顺序：

1. 改动文件定向检查、类型检查和对应回归。编辑器至少覆盖 E01–E09，新增用例要能发现具体退化。
2. 使用 [verify.yml](../.github/workflows/verify.yml) 串行完成 Node/核心单测，再调用 [native-verify.yml](../.github/workflows/native-verify.yml) 完成 macOS 原生与真库检查。
3. 前一步完成后，针对同一功能提交运行 [Windows MySQL WebView 验收](../.github/workflows/windows-mysql-acceptance.yml)。
4. 再运行 [Windows 安装包验收](../.github/workflows/windows-installed-candidate.yml)，验证关闭测试钩子的生产应用。用户试用同一已验收产物。
5. 按用户的单线程要求完成只读复核，记录范围、结果与无法验证项；用户试用后决定是否进入下一阶段。

P1.1 将两份 Windows 工作流接入 PR 的串行检查链：通用原生检查后运行 Windows WebView，再运行安装包验收；保留指定分支 push 和 workflow_dispatch 入口。运行后核对 headSha、实际检出的提交和候选 manifest；PR 上的合并测试提交与分支 HEAD 分别记录。不能只看单个 Node 检查绿色就宣布 Windows 安装版通过。

已有命令以 [package.json](../package.json) 和工作流为准，例如 `pnpm run typecheck:desktop`、`pnpm run test:native-ui-models`、`pnpm run test:core-unit --maxWorkers=1 --no-file-parallelism`。按实际改动选择必要检查，不把文档里的计划命令当成执行结果。

每次功能交付包含：聚焦的小 PR、测试对应的源码 SHA、GitHub 运行链接、Windows 候选包、简短操作说明、已知限制和回退提交。改重要文件前备份到仓库 backups/；不将凭据、个人配置或真实业务数据放入备份、日志、测试产物。

P1 尽量保持已有草稿持久化格式不变，以便回退编辑器提交。P2/P3 若增加持久化设置，先保证旧版本可读取或忽略新字段，并记录恢复方式。返回旧版本不等于回滚服务器已提交的数据。

合并、正式 Release、签名及公证单独按授权和发布流程执行。若出现错连目标、丢稿、数值精度损失、重复写入或提交结果误报，停止该候选的推广并优先修复。

## 9. 主要风险与处理

| 风险 | 处理与验证 |
| --- | --- |
| 新编辑器破坏中文输入或执行快捷键 | 首阶段覆盖 IME、补全打开状态与真实键盘操作；输入法组合期间不响应执行快捷键 |
| Vue 状态同步覆盖文本或撤销记录 | 单一文本更新路径，按标签维护编辑状态；测试历史载入、格式化和标签切换 |
| 编辑器语法判断与数据库实际语法不同 | 继续使用现有执行切分与参数逻辑；诊断标为辅助信息，不凭前端猜测修改 SQL |
| 新网格显示顺序与数据库列位置不一致 | 复制、粘贴、预览与写入都按稳定的列标识映射，测试隐藏列和同名列反例 |
| 多标签共享事务导致用户误判范围 | 统一展示连接级范围；逐表列出草稿和已应用状态；独立连接验证提交/回滚 |
| 新组件导致 UI 自动化失效 | 在接入阶段确认可访问性入口，更新 UIA/真实 WebView 场景，不降低断言换取绿色 |
| 范围逐渐变成全面追赶 dbx | 每阶段以具体用户任务验收，新增方向排到后续；当前阶段未认可前不扩展 |
| 将 PG 兼容误当作 Hologres 全部兼容 | 独立验证元数据、类型、取消与权限；未验证能力在界面明确禁用 |
| 云端查询已提交，本地超时后又执行一次 | 记录服务端任务标识，先查原任务；提交结果未知时提示核对，禁止自动重提 |
| 草稿、发布状态、DI 提交回执混淆 | 分别读取对应权威来源，保留更新时间；没有运行实例证据不显示执行成功 |
| 本地服务或鉴权状态变化导致功能失效 | W0 先验证版本与能力契约；服务不可用时保留草稿、提供恢复说明，不切换其他数据库入口 |

### 10.1 用户每天能够完成的流程

| 使用场景 | 工作台内的完整流程 | 完成标志 |
| --- | --- | --- |
| 临时查数 | 找项目/库表 → 看结构、注释和分区 → 生成明确列清单 → 查询 → 查看、复制或导出 | 结果来源、筛选范围、类型和是否完整都清楚 |
| 开发数仓 SQL | 查看源表 → 编写多层 CTE/JOIN → 核对字段 → 只读验证 → 保存本地 SQL | 补全不串作用域，字段有来源，SQL 可复现 |
| 排查任务失败 | 找节点 → 区分草稿与已发布版本 → 看依赖、参数和运行实例 → 看真实报错 → 跳转平台处理 | 能定位到具体节点/实例和失败阶段，不把异步提交当成功 |
| 检查上下游数据 | 固定分区/时间窗口 → 核对主键 → 两端查询 → 对比行数、金额和抽样字段 | 输出差异和口径，不静默改变类型、粒度或时间范围 |
| 准备变更交付 | 下载指定节点草稿 → 本地编辑 → 查看差异和参数 → 导出 SQL 与检查结果 → 跳转 IDE | 有可审阅的交付文件，不因保存本地草稿而写入生产 |
| 继续未完成工作 | 重开应用 → 恢复 SQL 与节点上下文 → 查询原任务状态 → 继续处理 | 不重复提交云端任务，不恢复虚假的数据库事务 |

操作界面沿用现有工作区：左侧按数据源与项目找对象，中间编写 SQL 或查看节点脚本，下方显示结果、任务状态和错误，详情区展示字段、分区或节点依赖。各区域跟随明确的对象上下文，不强制用户为每种引擎学习另一套操作。

### 10.2 接入原则与 W0 前置验证

规划以用户环境中的本地 `data-mcp` 为 Hologres/MaxCompute/DataWorks 能力复用入口，地址由本机配置绑定到 `http://127.0.0.1:8001/mcp`。由 Rust 后端适配服务，Vue 通过现有类型化后端桥调用；认证材料留在既有服务和受保护的认证流程中，界面只展示连接状态与恢复入口。

用户基线已给出 `holo_*` / `mc_*`、`submit_query(engine=...)`、表结构读取和 DataWorks BFF 等能力线索。当前仅依据用户基线与技能说明编制规划，未连接本地服务、未核对实时工具 schema，也未执行任何云端查询。下面的“查询状态、取结果、取消”等是必须满足的能力要求，不是已确认存在的具体 API 名称。

W0 交付一份实际接口映射，至少核实：

1. 服务版本与健康状态、允许访问的引擎/项目/库、表结构与分区获取方式。
2. 查询提交、服务端任务标识、状态轮询、分页/结果上限、取消和服务重启后的恢复能力。
3. DataWorks 节点定位、草稿、发布状态、依赖、运行实例与日志的只读接口，及浏览器跳转定位信息。
4. 类型、时区、错误、权限不足和鉴权过期的返回格式，以及版本不兼容时的明确处理。

已有能力满足时仅增加适配；缺失能力列出最小服务改动及工作量，明确仓库范围后再实施，不能擅自修改 `data-mcp` 所在项目或全局配置。单纯展示“不支持”可作为失败反馈，但不能让缺失的必选场景通过验收。若关键接口确实不可实现，应调整产品承诺和排期，再决定是否继续该阶段。

浏览器登录和 Cookie 恢复复用本机共享 Playwright 服务及既有 `get-dataworks-cookie` 流程；不另起浏览器、不连接 9222、不复制 Cookie 到应用配置或文档。共享服务不可用时保留草稿并说明需要恢复。用户的本机访问基线优先于技能文件中可能保留的历史取 Cookie 示例。

### 10.3 串行实施阶段

| 阶段 | 实施内容 | 阶段交付与验收重点 |
| --- | --- | --- |
| W0 接口与环境基线 | 完成第 10.2 节的能力核实；定义引擎、项目、对象与任务标识 | 一份实测接口映射和最小纵向原型；全部关键能力有明确结论 |
| W1 Hologres 查询 | 项目/库/schema 导航，表字段与注释，生成列清单，结果查看/导出，取消与权限反馈 | 在专用测试对象上真实查询；大整数、小数、时间、JSON、NULL 和空串可独立核对 |
| W2 MaxCompute 查询 | 项目、表、分区导航；异步提交/状态/结果；运行记录、Logview 入口及可用的取消 | 同一任务从提交追踪到真实终态；中途断开和重开应用不重复提交 |
| W3 数仓 SQL 编辑 | 按引擎提供语法与补全；CTE、派生表、嵌套 SELECT/JOIN 的作用域；分区检查与显式参数预览 | 常用多层 SQL 补全和参数展开正确；不支持的动态 SQL 明确提示，不编造字段 |
| W4 DataWorks 排障 | 节点查找、草稿/发布态区分、依赖与参数查看、运行实例和日志、平台定位 | 能从节点找到真实失败实例与报错；DI 异步提交回执不冒充成功 |
| W5 对账与本地交付 | 固定范围的跨源结果对比；本地脚本版本差异、参数/词根检查、交付文件导出 | 差异有原始查询和范围证据，文件一致且不触发线上写入 |
| W6 综合验收与试用 | 完成 12 个必选场景、断连/超时恢复、8 小时活动负载和 10 个工作日试用 | 约定日常任务可完成，关键问题关闭，用户确认可作为主力候选 |

**W1 的引擎边界。** 按真实权限展示对象，不把权限不足或接口失败显示成空库。读取元数据后再生成 SQL，按 Holo 语义保留类型和时区。首轮 Holo 接入以只读查询为验收范围，现有 MySQL 网格写入能力不会自动套到 Holo；Holo 写入另行按具体表和场景验证。

**W2 的任务语义。** 区分等待、运行、成功、失败、已取消、状态未知。拿到任务 ID 只表示已提交；以权威状态接口确认完成。网络中断、返回丢失或认证过期时，先核对原任务，绝不自动重提。取消请求发出不等于已经取消。分页使用接口实际支持的机制；结果受上限约束时显示截断标志，不能标为全量导出。MaxCompute 不套用 MySQL 的连接级提交/回滚语义。

**W3 的开发边界。** 补全依据当前引擎、项目和查询作用域，只使用已核实字段。`${...}` 调度变量和数据库绑定参数分开处理，未解析变量不能静默替换为空值。查询检查提示明确列、分区条件、小时表 dt/ht 和排序 LIMIT；任何修订都先展示，不暗中改写 SQL。读操作权限由服务端能力和账号共同限制，不能只靠 SQL 以 SELECT 开头就判断无副作用。

**W4 的事实来源。** SAVED 草稿按既有 `getFile` 通道读取；调度边依据 `getVertex.dependencies[]`，不能将输出名称当成调度边；发布/运行状态依据运维节点与周期实例。DI 真实执行依据实例 run_history 和数据集成日志，wrapper 的 exit 0/FINISH 只能作为提交信息。展示读取时间、项目和节点/实例标识；不把节点名称相似当作同一对象。默认项目来自已确认配置，跨项目时明确显示目标项目。

**W5 的数据边界。** 对账先明确粒度、主键、分区/时间窗和两端数据截止时间；对齐失败就报告不可比较。首版支持约定范围内的行数、主键重复、金额汇总与抽样字段对比，后续再扩展有界的逐行比较。超过范围或结果上限时不能输出“全表一致”；迟到数据与快照时间差必须可见，不生成自动同步写入。

**W5 的交付范围。** 用户选择本地工程目录，导入指定节点脚本并记录来源版本，在本地编辑、看 diff、检查参数和导出。需要 DDL 时先核实现有表结构，再调用可用的词根校验；DDL/DML 列映射检查给出具体差异。通用语法预检和词根检查不代表云端 SQL 已编译通过。生产建表、更新节点、改依赖/调度和发布均不由本规划授权；用户在 IDE 提交，后续如需应用直接写入，必须针对具体表/节点另行明确授权和验收。

### 10.4 两类验收证据必须同时具备

| 证据来源 | 验证内容 | 不能据此得出的结论 |
| --- | --- | --- |
| GitHub Actions | 桌面构建、安装包、界面操作、适配协议、类型精度、分页/超时/权限故障模拟与状态恢复 | 模拟的成功不能证明企业云环境真实可用 |
| 用户授权的私有环境 | 同一候选包通过本地服务访问专用 Holo/MC 对象和 DataWorks 测试节点，独立回读与实例核对 | 只跑接口不能证明生产安装包里的交互可用 |

顺序先 GitHub、后私有环境。普通 GitHub 托管运行机不访问用户内网服务，不注入用户 Cookie、数据库口令或业务数据。私有环境运行方式在 W0 核实，优先由用户本机运行 GitHub 生成的候选包；如使用私有 runner，须单独确认可用性和权限，不默认已经存在。

回执记录应用 SHA/安装包哈希、本地服务版本、场景编号、时间和结果。完整实例定位信息保留在受控本地记录；公开 PR/Actions 只放脱敏结论与合成数据证据。无真实服务证据的项记为“未验证”，关键场景未验证时不能放行为数仓主力候选版。

第二轮估算置信度较低，前提是本地服务的核心接口可复用、测试资源可用、无需大规模重写驱动。W0 完成后必须按接口缺口和复杂 SQL 的实际范围重估，不能将此数字解释为交付承诺。P0 阶段只做一次轻量依赖核对，及早识别第二轮不可行条件；正式 W0 在第一轮结束后串行实施。

## 11. 保留到后续的产品能力

复杂表结构图形化编辑、Excel 导入、全库搬运/备份恢复、其他数据库、AI 对话和插件市场，当前仍不属于数仓主力版的必选场景。它们对通用数据库管理有价值，但需按用户实际任务单独排期。

如实际试用表明其中某项是日常不可缺少的能力，应在进入相应阶段前正式加入范围、补验收并重估预算；不能在交付时才发现“主力工具”遗漏必需任务。具体应用写生产节点或执行生产 DDL/DML 的功能同样需独立设计与授权，不能用通用“继续开发”代替。
