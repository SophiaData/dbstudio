## 1. 判断与规划假设

项目已经越过架构验证阶段：连接管理、元数据、查询、表格编辑和桌面 GUI 均有实际代码与测试。当前更适合定位为“功能较丰富、正在补齐可靠性的早期客户端”，尚不能仅凭功能数量或本地测试通过判断已达到稳定发行水平。

下一阶段最有价值的投入是完成现有工作流：看见哪个标签，就操作哪个标签；有未提交事务，就始终看得见；声称完整导出，就不丢字段内容；包能构建，也必须能离开仓库运行。

本规划采用以下假设，后续可按用户反馈调整：

- 首批用户是日常使用 SQLite/PostgreSQL 的开发者和数据工程师。
- 桌面客户端为主线；SDK 保持可交付，但不同时扩成第二条完整产品线。
- 按 1 名熟悉 TypeScript/Electron 的全职开发者估算，阶段串行约 28–43 个工作日，约 6–9 周；这是工作量区间，不是固定交付承诺。
- 优先级按数据正确性、现有功能闭环、交付质量、新能力排序。
- 尚未核验远端 CI 运行结果、GitHub Release 产物、npm 发布记录；不对线上状态作结论。

## 4. 优先解决的问题

### P0：多标签操作对象一致性

`src/renderer/main.ts:103` 单独记录 `activeGrid/activeTableRef/activeSql`，而 `src/renderer/tabs.ts:215` 切换标签只更新自己的状态。切回旧标签时，外部工具条可能仍指向最近打开的结果；筛选又使用树最近选择的连接。清除筛选时，基准 SQL 已被过滤后的 SQL 替换。

**目标：**由标签对象统一提供连接、来源、原始查询、网格和筛选状态。导出/筛选使用当前可见标签的上下文。失败结果必须保持失败提示。

### P0：事务状态与离开保护

`src/renderer/grid.ts:1322` 应用成功会清空本地 dirty；`src/renderer/grid.ts:475` 重置只在 dirty 非空时尝试回滚；`src/renderer/tabs.ts:240` 关闭标签直接释放网格。事务属于连接，当前界面状态却主要保存在各网格中，可能出现离开后仍存在不可见未提交事务，或局部回滚影响同连接其他标签。

**目标：**区分本地未应用编辑与数据库未提交事务。连接级统一显示事务状态；关闭、刷新、断连和退出时明确影响范围，提供提交/放弃/取消。不能直接把某个标签的“放弃”默认为回滚整个连接。

### P0（SDK 发布阻断）：包外运行失败

已复现，见本次验证。涉及 `sdk/package.json:34`、`sdk/build.mjs:84`、`sdk/test/sdk.e2e.mjs:19`。

**目标：**明确运行时依赖策略；tarball 在仓库外安装后按包名导入，宿主可启动、SQLite 可查询、类型可编译。根据实际测试确定 Node 下限，不能继续只依赖仓库根目录的依赖。

### P1：导出完整性

`src/renderer/tabs.ts:468` 的 CSV 序列化使用 `cell.text` / `previewBase64`，未恢复被截断内容；前端收集全部行后再生成下载文件。

**目标：**近期先明确预览导出边界，检测截断并阻止误报完整成功；随后通过专用导出任务逐批写文件，提供进度与取消。对任意 SQL 的完整值不能盲目逐格补查，应验证现有 `fetchCellValue` 的适用范围与查询一致性。

### P1：现有查询体验的方言差异

`src/renderer/main.ts:340` 固定拼接 `EXPLAIN QUERY PLAN`；`:320` 的补全缓存未按连接隔离；`:327` 仅遍历直接 folder，不能覆盖 PostgreSQL schema 层级。

**目标：**执行计划由方言能力提供；候选按连接/schema 缓存，切换连接立即失效；不支持的能力给出明确状态。

### P1：验证与发布清单漂移

`package.json:21` 包含 SQL 库存储与 GUI 测试，`.github/workflows/verify.yml` 未接入；`.github/workflows/release.yml:83` 每个平台直接上传并公开 Release，缺少等待全部平台成功后的统一发布步骤。当前验证也没有从实际安装产物启动。

**目标：**测试清单只有一个维护入口；发布等待所有必需平台验收完成；tag 与应用版本一致；手动构建不自动公开发行。

### P1：连接异常恢复与临时凭据

`src/main/DriverHostHandle.ts:161` 在退出时拒绝挂起请求，但 manager 没有相应退出回调来清除 live 状态。`src/main/ConnectionManager.ts:384` 在存在 live 记录时直接返回；`:420` 建连只从存储读取凭据，`:333` 新建连接在凭据无法保存时未将输入继续传给本次会话。

**目标：**先补故障注入测试验证实际表现。宿主退出后能反映断连并重连；安全存储不可用时本次输入仍可用于本次连接，同时不写入明文。并发重连只创建一个宿主；退出后回收进程与游标。

## 7. M1 的执行结果契约（由 T2/T3 的状态模型推出）

M1 的第一件事不是加功能，而是**定义执行一条 SQL 会返回什么**。当前的
`runQuery` 只能返回「只读结果集」，写语句塞进去既没有影响行数，也说不清
事务状态——这正是 M0 事务模型要解决却没解决的根。

**必须区分的三类结果**（而不是塞进同一个 `result` 字段）：

| 类型 | 何时产生 | 必须携带 |
|---|---|---|
| `rows` | SELECT / RETURNING 等返回行的语句 | 现有的 `QueryResult` + 游标 |
| `affected` | UPDATE / INSERT / DELETE | 影响行数、是否进入事务、事务状态 |
| `ddl` | CREATE / DROP / ALTER 等 | 变更摘要（建了什么、改了什么）、是否已提交 |

**硬约束：**

1. **写语句绝不进只读分页接口。** 不能把 `affected` 塞进 `QueryResult.rows`
   再靠 UI 判断——那会让「返回 0 行」和「影响了 0 行」永远分不清。
2. **写语句的结果必须落到连接级事务控制器上**，沿用 M0 已建立的
   「本地编辑 / 已应用事务」两层区分，不另起一套状态。
3. **DDL 与 DML 的提交语义要分开。** DDL 在多数库里会隐式提交，
   不能沿用 DML 的「应用 / 提交 / 回滚」三段式——那会给出错误的承诺。
4. **失败必须有可定位的错误**：哪条语句、哪个连接、数据库返回了什么。
   「执行失败」四个字不足以定位问题。

**M1 的验收标准（承接 Beta 最低标准）：**

在 SQLite 与 PostgreSQL 上都能完成
「查询 → 写入 → 看到影响行数 → 提交或回滚 → 失败后能恢复到一致状态」，
并且写操作**不需要**依赖数据库权限之外的额外限制。

## 8. 工程与验收原则

- **保持架构边界。**不将 adapter 导入 main/renderer；新方言同时维护实现注册与纯元信息，并用测试检查清单一致性。
- **按工作流拆模块。**`grid.ts` 2284 行、`tree.ts` 1919 行、`main.ts` 1201 行，两个 adapter 均超过 1500 行。随任务抽出标签上下文、事务控制、导出任务；不安排无明确收益的全量重写。
- **先确立契约再并行。**两人协作时可将打包/CI 与 UI 状态修复并行；SQL 执行和导入共享契约，不能独立各写一份。
- **测试验证实际后果。**数据库最终值、实际导出字节、实际安装包和进程数比“按钮存在”“调用过函数”更有说服力。
- **性能先记录再优化。**M3 固定机器与夹具，记录首屏时间、深分页延迟、持续滚动内存、重复开关标签后的进程/游标数，以及导出吞吐；本次不凭空给出性能达标结论。
- **发布可追溯。**保存 commit、环境、测试通过/失败/跳过数、构建版本、平台产物与校验结果；所有必需平台完成后统一公开发行。
- **试用反馈进入排期。**招募 3–5 名目标用户完成真实连接、查询、修改、恢复、导入导出任务；按阻断频率和数据影响排序，不把功能投票直接等同优先级。

## 9. 阶段成功标准

Beta 的最低成功标准是：用户从安装开始，能够安全连接 SQLite/PostgreSQL，明确知道查询和修改作用于哪个连接，在多标签中正确管理事务，保存并找回 SQL，导出完整数据，并在断连、重启或升级后恢复正常工作。

“支持数据库数量”“功能菜单数量”和“单次测试全绿”不作为单独完成标准。首个推进点是 M0：让已有能力的正确性与交付证据配得上当前功能范围。
