### A1-R1 [P1] 忽略大小写提取主键，可能合并不同记录的编辑身份

**位置：**`/Users/gaotingkai/Projects/dbstudio/src/renderer/grid.ts:355`，`#extractKeyValuesFromRow`。

**证据：**查找主键列使用 `c.name.toLowerCase() === kc.name.toLowerCase()`，返回第一个匹配列。

**触发场景：**PostgreSQL 表同时存在 `"id"` 与 `"ID"`，主键为 `"ID"`，结果列中 `"id"` 位于前面。两条记录分别为 `(id=7, ID=10)` 和 `(id=7, ID=20)` 时，提取出的主键快照都成为 `ID=7`，进而生成相同的脏编辑索引。

**影响：**两个不同主键的记录共用一个暂存记录，后续编辑可能覆盖先前编辑。此结论针对 renderer 的身份提取与缓冲合并；实际数据库写入行为还需同时核对驱动解析，不能把本文当作“数据库改错行已由审核者复现”的证据。

**修正与验收：**

- [ ] 按真实列名精确提取主键；无法唯一确定时明确拒绝。
- [ ] 补充大小写不同列名且非主键值相同的回归，断言两个编辑身份不会合并。
- [ ] 核对 PostgreSQL 驱动的列名解析，验证端到端写入目标；若发现既有问题，说明归属与处理范围。

### 6.3 A1-R1 延续 [P1] PG 大小写不同的组合主键仍会丢失一个键条件

**位置：**

- `/Users/gaotingkai/Projects/dbstudio/src/drivers/postgresql/adapter.ts:1418`
- `/Users/gaotingkai/Projects/dbstudio/src/drivers/postgresql/adapter.ts:1429`
- `/Users/gaotingkai/Projects/dbstudio/src/drivers/postgresql/adapter.ts:1459`

虽然本轮修复了 `resolveColumns`，上述主键覆盖检查及有序匹配仍使用小写比较。若表的组合主键为 `("id", "ID")`，传入两列后，匹配 `"id"` 和 `"ID"` 都会命中同一条首个记录，生成重复的 `"id"` 条件。

例：存在 `(id=7, ID=10)` 和 `(id=7, ID=20)`，编辑第一行应使用两个不同主键列。当前路径会把 WHERE 降为 `"id" = 7 AND "id" = 7`，遗漏 `"ID" = 10`，可能更新两行。`affected > 1` 的错误在 SQL 写入后才返回，`applyEdits` 保留事务且未逐行撤销这次写入；报错不能等同于没有误改。

这是上轮要求核对驱动路径后仍未完成的既有问题，不声称该 adapter 缺陷由本轮新引入。源码链路可确认，真实 PG 行为本轮未运行。

**关闭条件：**

- [ ] 主键完整性校验及有序匹配使用已经解析出的真实列名，不能再次按小写合并。
- [ ] 覆盖大小写不同的组合主键 UPDATE，并检查共用解析路径的 DELETE。
- [ ] 实际验证只改变目标行；缺少任一键必须拒绝。若无 PG 环境，提交真实生产路径的 SQL/参数测试，并明确保留 PG 端到端待验证。

### 6.4 A1-R5 [P1] 查询轮次保护未覆盖分页返回，旧页仍可污染新结果

**位置：**`/Users/gaotingkai/Projects/dbstudio/src/renderer/grid.ts:1928`、`/Users/gaotingkai/Projects/dbstudio/src/renderer/grid.ts:1939`。

本轮 `#queryEpoch` 只在 `#openCursor` 的初始结果返回时检查。`#loadPage` 发出请求后，不核对轮次或当前游标就写入 `#pages`、`#knownRows`、`#exhausted`；finally 也无条件删除同页的 inflight 记录并重绘。

触发顺序：旧游标分页请求尚未返回 → 排序或广播刷新建立新结果 → 旧分页响应返回。旧页会被装入新查询的缓存，与新第一页混合；如果新轮次也请求同页，旧请求的 finally 还会删除新请求的去重记录。

这是异步刷新验收要求仍未覆盖的路径，不把原本存在的分页缺口误称为本轮独有回归。即使编辑已有稳定主键，结果显示和后续按行号读取全文等操作仍不能混用两个游标的数据。

**关闭条件：**

- [ ] 分页成功、失败、finally 均核对所属轮次与游标，只清理属于本请求的 inflight 记录。
- [ ] 排序、广播刷新和 dispose 后，旧请求不得改变缓存、状态栏、耗尽标记或重绘已销毁网格。
- [ ] 用真实 ResultGrid 加可控 API Promise，制造“旧分页迟于新查询返回”的顺序；断言缓存/可见内容与游标归属一致。

### 6.5 A1-R6 [P2] 丢弃旧查询结果时未关闭它新建的游标

**位置：**`/Users/gaotingkai/Projects/dbstudio/src/renderer/grid.ts:670`。

检测到过期轮次后直接返回 `{ result, error: null }`，没有释放 `result.cursorId`。该游标尚未赋给 `#cursorId`，后续 reset/dispose 只关闭当前游标，无法再追踪它。

PG adapter 的游标在 `#cursors` 中登记，并依赖 close/disconnect 清除；因此重复并发刷新会积累未释放的游标记录。这是本轮新增的丢弃分支需要承担的资源清理，不只是界面是否显示旧数据的问题。

**关闭条件：**

- [ ] 丢弃带游标的响应时释放该游标，不关闭较新请求的活动游标。
- [ ] dispose 使未完成查询失效，迟到响应不重新占用已销毁网格的资源。
- [ ] 在真实网格路径中断言旧游标被关闭、新游标仍可用；不要只断言最终文字为 fresh。
